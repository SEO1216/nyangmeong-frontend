# 펫돌봄 일정 기한·채팅 종료 처리 백엔드 요청서

백엔드 저장소에서 `/start`로 기획할 때 붙여 넣는다. 클래스 이름은 백엔드 코드를 읽어 확인한 것이다(2026-11-13 커밋 기준). 그 뒤에 바뀐 곳이 있을 수 있으니 이 문서의 "구현해야 한다"는 문장은 그 저장소의 최신 코드로 한 번 맞춰 본다. 결정 전인 항목은 따로 표시했다. (작성 2026-11-13, 정리 2026-11-15, KSJ)

## 한눈에 보기

| 순서 | 항목 | 서버 작업 | 절 |
| --- | --- | --- | --- |
| 먼저 | 나가기 차단·메시지 차단이 이미 구현됐는지, 읽기 전용 방을 되살릴 때 입력이 막히는지 | 확인(시험) | 4번, 6번 |
| 1 | 글 등록·수정 날짜 기한 검증 | 구현 | 1번 |
| 2 | 지난 글 자동 마감 배치와 「매칭 이력 있음」 응답 값 | 구현 | 2번 |
| 3 | 완료 글 7일 뒤 공개 목록 숨김(내 글만 보기는 계속 보임) | 구현 | 3번 |
| 4 | 거래 취소 요청(매칭 완료 이후) | 별도 기획 | 5번 |
| 결정 | 무응답 기한, 개인정보 보관 기간 등 | 팀 결정 | 6번 |

**서버 작업이 필요 없는 것**(프론트만 바뀐다. 알고 있으면 되고 서버에서는 건드리지 않는다)
- 채팅 목록 개편(탭, 안 읽음 칩, 정렬, 편집 모드).
- 채팅방 지우기: 새 API 없이 기존 `POST /chat-rooms/{sn}/leave`를 방마다 호출한다(3번).
- 종료된 채팅방을 목록에 계속 보여 주는 것: 지금 쿼리가 이미 그렇게 동작한다(참여 상태 `JOINED`인 방만 조회, 기간 조건 없음).

## 0. 확정된 정책

| 항목 | 값 |
| --- | --- |
| 돌봄 시작일 | 오늘부터 90일 이내 |
| 돌봄 종료일 | 시작일부터 30일 이내 |
| 일정 협의 가능 글 | 작성 후 30일이 지나면 마감 |
| 종료일이 지난 모집중 글(매칭 없음) | 지난 날 바로 마감 |
| 완료 글 공개 목록 숨김 | 완료 후 7일 (삭제 아님, 숨김). 작성자의 「내 글만 보기」에는 계속 보임 |
| 종료 채팅방 | 숨기지 않고 유지. 회원이 직접 나가기(지우기)할 때만 내 목록에서 사라짐. 기존 `leave` 재사용(2026-11-15 결정) |
| 나간 방에서 「채팅하기」 재시도 | 지금처럼 기존 방을 되살린다(2026-11-15 결정, 6번 참고) |

프론트는 날짜 선택기와 폼 검사에 90일·30일을 이미 넣었다. 서버 검증이 없어 API를 직접 부르면 우회된다.

## 1. 글 등록·수정 날짜 기한 검증

- 대상: `CareRecruitmentCreateRequest`, `CareRecruitmentUpdateRequest`의 `prtcBgngDt`·`prtcEndDt`.
- 시작일이 오늘 이전이거나 오늘+90일 이후면 `INVALID_INPUT_VALUE`.
- 종료일이 시작일+30일을 넘으면 같은 오류.
- 수정에서 날짜를 바꾸지 않았다면 이미 지난 날짜여도 저장을 허용한다(프론트와 같은 규칙).

## 2. 지난 글 자동 마감 (배치)

- `CareMatchNoResponseJob`처럼 community 안에 새 배치를 둔다. 매일 00:00 KST 실행을 제안한다.
- 대상: `RCRT_STTS=PCAC0001`(모집중)이고 매칭이 없는 글.
  - 일정이 있는 글은 `prtcEndDt`가 지난 글.
  - 일정 협의 글은 작성 후 30일이 지난 글.
- 처리: 글 상태를 `PCAC0003`으로 바꾼다. 상태 변경 이력은 기존 `changeRecruitmentStatus`를 쓴다.
- 매칭 완료 이후 단계는 건드리지 않는다(거래 진행 중).
- 응답에 구분값 추가: 화면이 매칭 없이 마감된 글을 「모집 종료」, 실제 거래가 끝난 글을 「거래완료」로 나눠 보여 준다. 목록·상세 응답에 "매칭 이력이 있었는지" 값이 필요하다. 필드명은 서버 규칙에 맞게 정한다. 프론트는 그 키를 그대로 쓴다.

## 3. 완료 글 7일 숨김, 종료 채팅방 유지

- 펫돌봄 글 목록: `RCRT_STTS=PCAC0003`이고 완료 후 7일이 지난 글을 공개 목록에서 제외한다. 작성자·돌봄 제공자 등 당사자가 「내 글만 보기」(`mineYn=true`)를 켜면 기간과 관계없이 포함한다. 상세 조회는 막지 않는다(채팅방 「돌봄 글 보기」 링크).
- 숨김 일수 `7`은 글 공개 목록에만 적용하며 시스템 설정값(`SYS_STNG`)으로 두면 운영 중에 바꿀 수 있다.
- 채팅 목록(`ChatRoomSummary`): 종료된 방(`chatRoomSttsCd`가 읽기 전용 `CHTC0002`이거나 매칭 상태 `EXPIRED` `PCAC0018`)을 **기간으로 숨기지 않는다.** 종료 후에도 당사자의 채팅 목록과 내용 열람이 계속된다(`ChatRoomMapper.xml`의 목록 쿼리가 이미 이렇게 동작한다). 새 메시지는 4번대로 막는다.
- 지우기: **새 API는 필요 없다. 기존 `POST /chat-rooms/{sn}/leave`(`ChatRoomService.leave`)를 재사용한다.** 이 API는 이미 내 참여 상태만 `LEFT`로 바꿔 내 목록에서 숨기고 상대 쪽에는 남긴다. 종료된 방에서는 `CareMatchService.cancelOnLeave`가 `!isInProgress`로 바로 돌아가 매칭 취소·시스템 메시지·상대 알림이 없다(2026-11-15 코드 확인). 화면은 종료된 방을 목록에서 여러 개 골라 방마다 이 API를 호출한다. 진행 중인 방은 4번의 나가기 차단 규칙을 따른다. 양쪽이 모두 나간 뒤의 실제 삭제·보관은 개인정보 보관 기간 결정(6번)과 함께 정한다.

## 4. 채팅 서버 차단 (구현 여부부터 확인)

- 종료 방 메시지 차단: `ChatMessageService`가 방이 읽기 전용이거나 매칭이 `EXPIRED`이면 새 메시지를 거부한다. 프론트는 입력창과 사진·위치 버튼을 이미 막았다(막는 문구는 프론트가 「상대방과 더 이상 대화할 수 없어요」 하나로 통일한다. 서버가 이유를 구분해 줄 필요는 없다).
- 나가기 차단: `leave`가 매칭완료·확인 대기·수령 대기(`PCAC0013`·`PCAC0014`·`PCAC0015`)에서는 거부한다. 프론트는 메뉴만 비활성화했다. 2026-11-13 코드의 `ChatRoomService.leave`(110~121행)에는 이 차단이 없었다. 이미 구현됐다면 이 항목은 지운다.
- 참고: 목록의 일괄 삭제가 진행 중인 방에 호출되어도 지금은 서버가 막지 않는다. 위 나가기 차단이 구현되면 함께 해결된다.

## 5. 거래 취소 요청 (매칭 완료 이후) — 정책 승인됨, 상세는 기획에서 확정

현재 `CareMatchController`의 `cancel`은 수락 전(`REQUESTED`) 전용이다. 매칭 완료 뒤에는 나가기가 유일한 취소 수단이어서, 4번의 나가기 차단과 반드시 같이 가야 한다.

- 요청: 매칭완료·확인 대기·수령 대기 단계에서 사유(코드+내용)와 함께 요청한다. 사유는 필수이고 시안은 다음과 같다.
  - 일정이 맞지 않게 됐어요
  - 상대와 연락이 어려워요
  - 조건이 달라졌어요
  - 기타(직접 입력 필수)
- 상대가 동의하면 거래가 취소(`PCAC0017`)되고 방이 읽기 전용이 되며, 글 상태는 모집중으로 되돌린다(기존 `cancelOnLeave`와 같은 처리).
- 상대가 거절하면 거래가 이어지고, 요청자가 철회할 수 있다.
- `GET /chat-rooms/{sn}` 응답에 취소 요청 정보(요청자, 사유, 상태)를 실어 준다. 화면이 요청한 쪽·받은 쪽 카드를 이걸로 그린다.
- 시안: https://claude.ai/artifact/AUy2P1X6vTR1Ep4Qyy9zR5 (로그인한 본인 계정에서만 열림. 필요하면 아래 5단계로 복원)
  1. 채팅방 메뉴: 「거래 취소 요청」 추가, 「채팅방 나가기」는 흐리게 막고 안내
  2. 요청 확인 창: 사유 선택(필수) + 「취소 요청 보내기」
  3. 요청한 쪽 카드: 대기 표시 + 「요청 철회하기」
  4. 받은 쪽 카드: 사유 + 「취소에 동의」·「거절하고 계속」
  5. 취소 완료: 입력창 읽기 전용, 나가기 켜짐
- 정해야 함: 상대가 응답하지 않을 때의 기한(자동 철회, 자동 취소 등).

## 6. 팀 결정이 먼저 필요한 것

| 항목 | 현황 | 선택지 |
| --- | --- | --- |
| 수령 대기 무기한 | `CareMatchNoResponseJob`이 수령 대기를 종료하지 않는 것은 2026-11-06 사람 결정. 보호자가 수령을 확인하지 않으면 글이 영원히 매칭완료이고 두 사람은 나갈 수도 없음 | 알림(7일·12일째) + 14일 자동 완료 추천 / 분쟁 접수 |
| 거래 취소 요청 무응답 기한 | 미정 | 자동 철회 또는 자동 종료 |
| 나간 방에서 「채팅하기」 재시도 | 2026-11-15 결정: 지금처럼 기존 방을 되살린다(`ChatRoomService.create`의 `rejoin`, 글·지원자당 방 하나). 이전 대화가 이어진다. 확인 필요: 되살릴 때 참여 상태만 `JOINED`로 바꾸므로, 요청 취소·상대방 나감으로 읽기 전용이 된 방은 재시도해도 입력이 막혀 있을 수 있다 | 그대로 / 되살릴 때 방을 다시 열기(`ACTIVE`) |
| 개인정보 보관 기간 | 미정 (숨김과 별개). 채팅 내용과 양쪽이 지운 방의 보관도 여기서 정한다 | 1년 후 주소·사진·채팅 정리 등 |

## 프론트 후속 작업 (서버와 무관하게 먼저 진행, 서버가 끝나면 이어서)

서버와 무관(지금 진행):
- 채팅 목록 개편(2026-11-15 시안 확정): 「전체」 탭 제거(내 글·지원한 글 두 탭), 안 읽음 칩을 「편집」 왼쪽에, 줄의 「돌보미」「보호자」 표시 제거(이미 반영됨), 글 상세에서 열면 그 글의 채팅을 맨 위로(색은 그대로).
- 열릴 때 탭: 글 상세에서 열면 「내 글」(채팅 목록 보기)·「지원한 글」(채팅하기), 헤더 아이콘이면 안 읽은 메시지가 있는 탭(둘 다이거나 없으면 「내 글」). 선택 탭이 아닌 쪽에 안 읽은 메시지가 있으면 탭 이름 옆에 점을 보인다.
- 채팅 불가 표시: 읽기 전용·만료·상대방 나감·탈퇴로 대화할 수 없는 방만 목록에서 내용을 흐리게 보이고(거래 완료·요청 취소처럼 채팅이 되는 방은 선명), 입력창 플레이스홀더는 「상대방과 더 이상 대화할 수 없어요」 하나로 통일하며 입력창과 사진·위치 버튼을 모두 비활성으로 둔다. 노란 띠는 내가 눌러 처리해야 할 알림이 있을 때만 쓴다.
- 목록 「편집」 모드: 종료된 방만 체크해 아래 「N개 삭제」로 기존 `leave`를 방마다 호출. 채팅방 메뉴는 「채팅방 나가기」 그대로.
- 일정이 지난 매칭완료 글의 안내 문구는 서버 없이 프론트에서 바로 가능.

서버가 끝난 뒤:
- 「모집 종료」 구분 표시(2번), 글 공개 목록 숨김 반영(3번).
- 거래 취소 요청 화면 5단계 (서버 응답 필드명을 그대로 사용, 5번).
